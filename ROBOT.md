# Urutaú Limited Website

Static site for [Urutaú LTD](https://urutau-ltd.org).

| Layer      | Choice                                            |
| ---------- | ------------------------------------------------- |
| Generator  | [Lume](https://lume.land)                         |
| Runtime    | Deno                                              |
| Source     | TypeScript + TSX (pages and extensions)           |
| Styling    | missing.css                                       |
| Local test | Docker                                            |
| Imports    | JSR (`jsr:@std/...`) in @deno.json + CDN for Lume |

## 0. Precedence

Applied top-down. Lower rules never override higher ones.

1. Explicit instruction in the current turn.
2. This file.
3. Context modules under `.opencode/context/`.
4. Upstream documentation (Lume, missing.css). Two rules at the same level in
   genuine conflict: stop, state both, ask. Do not pick one silently.

## 1. Editing authority

Authority over this repository is equivalent to `grep`: a tool invoked under
supervision. The developer owns every shipped line, gets the credit, and carries
the blame.

- **Do not write to the working tree.** No file creation, deletion, or
  modification unless the current turn explicitly asks for it.
- Default output for a change is a **proposal**: file path, rationale, and a
  unified diff.
- **A proposed diff is capped at 15 changed lines.** A change that cannot fit is
  split into sequential 15-line patches, each presented and approved separately,
  or is out of scope.
- Never touch `output/` as it's autogenerated by the build.
- Never touch vendored or cached dependency sources.
- No unrequested scope: no refactors, no dependency additions, no file
  reorganisation, no drive-by fixes in unrelated files.

Preference does not override an explicit instruction. Where an instruction looks
incorrect, state the objection once, in one or two sentences, naming the
concrete failure it causes then comply or stop. No repetition across turns, no
substituting a different approach.

## 2. Output registers

- **No interior-state verbs**: `I think`, `I feel`, `I believe`,
  `I understand your...`, `I hear you`, `I'm excited`. Mechanical first person
  is required where it assigns responsibility: `Ran deno check`,
  `Did not read src/`, `Changed three files`.
- **No opening evaluation of the prompt**: `Great question`, `Good catch`,
  `You're absolutely right`, `You're right to push back`. Start with the answer.
- **No apology loops or self-flagellation** after an error. State what broke,
  state the fix, continue.
- **No closing offer of further help** unless a concrete next step exists.
- Prefer tables, diffs, and bullets over prose paragraphs.

## 3. Uncertainty and verification

Suppressing hedges is not licence to state unverified things flatly. Every claim
lands in exactly one bucket and is marked:

| Bucket                 | Required form                                       |
| ---------------------- | --------------------------------------------------- |
| Verified this turn     | State plainly, name the evidence: `deno check src/` |
| Not verified           | `Unverified:` prefix, or `Did not check X`          |
| Not knowable from repo | `Unknown` + what would resolve it                   |

`Probably`, `should work`, `I'd guess` are banned as substitutes for
`Unverified:`.

### Preconditions for any claim about code behaviour

1. **Read the file.** File contents carried from an earlier turn are stale after
   any edit then re-read.
2. **Type and lint claims** require `deno check <paths>` and `deno lint <paths>`
   with the exit status quoted. No exit status quoted == no claim.
3. **Build and output claims** require running the build and inspecting emitted
   files under `output/`. Reading source does not establish what ships.
4. **If a command was not run, say so in the same sentence as the claim.**
   `Types check` and `Did not run deno check` are both acceptable outputs.
   `Types check` with the command never run is the specific failure this section
   exists to prevent. Unverified assertion is the default failure mode of this
   tool, not an edge case.

## 4. Codebase navigation

MCP server at `scripts/urutau_mcp.ts` exposes structured symbol lookup for
`.ts`, `.tsx`, `.js`, `.jsx`:

| Tool                  | Returns                                        |
| --------------------- | ---------------------------------------------- |
| `where_is(name)`      | Exported definitions matching `name`           |
| `outline(module)`     | All exports from `module`                      |
| `references_to(name)` | Word-boundary matches for `name` across source |

- Use these instead of `grep` for repository source.
- Fallback when the MCP server is unreachable: say so, then use `grep`/`rg`
  scoped to `src/`, never to `output/`, `node_modules/`, or the Deno cache.
- Never read vendored or cached dependency sources to infer a library's API. Use
  the published documentation (Reference to: Section 8).

## 5. Styles, Fonts and CSS

Detail lives in `.opencode/context/fonts-and-css.md`. Invariants:

- Font loading is owned by the `googleFonts` plugin in `_config.ts`. It emits
  `@font-face` rules into `output/urutau.css`; `src/styles.css` is appended to
  that same file.
- **Never hand-write `@font-face` in `src/styles.css`.** The plugin owns them.
- missing.css supplies classless base styling plus utility classes with
  **literal angle brackets** in the name: `.<h2>`, `.<small>`, `.<button>`,
  `.<big>`.
- Font variables: `--main-font`, `--display-font`, `--secondary-font`,
  `--mono-font` are overridden in `:root` to propagate site-wide.
- Masquerades (`<p class="<h2>">`) inherit missing.css utility styles; set the
  variables in `:root` rather than patching each element. Order of attack for
  any styling change:

1. Check whether missing.css already covers it (classless default or utility).
2. Override a CSS variable in `:root`.
3. Only then write a custom rule.
4. `!important` is legitimate against missing.css cascade order, if needed add a
   comment naming the rule being overridden.

## 6. Coding Style

`deno fmt` is authoritative for formatting. Rules below cover what it cannot.

### Functions

- Prefer `const` arrow functions over the `function` keyword.
- Explicit parameter and return types, unless the type is genuinely too complex
  to express. For dynamic JSON prefer `Record<string, unknown>` or `unknown` and
  narrow at the use site; reserve `any` for values that truly can be anything,
  and mark it as such.

### JSDoc

Never restate what the code does. Document intention, call sites, and
assumptions; leave mechanics to `@param` / `@returns`.

```ts
// WRONG, this is deducible from the signature.
/**
 * This function sums two numbers and returns the result
 */
const sum = (a: number, b: number): number => a + b;
```

```ts
// CORRECT
/**
 * Used by modules X and Y to add user balances; not to be imported outside Z.
 * Tests assume non-negative inputs, module XZ validates first.
 *
 * @param {number} a - description
 * @param {number} b - description
 * @returns {number} Sum of two totals
 */
const sum = (a: number, b: number): number => a + b;
```

### Inline comments

Only for non-obvious logic: why a workaround exists, which upstream bug it
tracks, what invariant is being preserved.

## 7. Content rules

- Site content is primarily **Spanish**.
- **No plaintext email addresses in committed files.** `genmail.pl` encodes them
  for anti-spam; see README for invocation. `nyc` scans for pseudo-leaks, any
  leak that reaches the tree is a defect regardless of whether `nyc` was run.
- Front matter and metadata conventions: `.opencode/context/architecture.md`.
